# Peek v2.1.0 — "Structured Value" Revision

**Date:** 2026-07-12
**Status:** Approved design, pending implementation
**Package version:** 2.0.0 → 2.1.0 (additive; schema strictness retained)

## Motivation

The first production PTP deployment (offers.com, via the FetchRight enforcer + offers-peek
tooling service) delivers real agent value, but roughly half of that value is delivered
_outside_ the schema:

- The live response fails the spec's own validator: `contentType: "ecommerce:deals"` is not
  in the closed `contentType` enum.
- The 500-char `snippet` carries four jobs at once: preview text, agent routing instructions
  ("Offer redemption URLs are in signals.codeOffers"), related-store links, and protocol
  attribution. Only the first is what `snippet` is for.
- Structured, typed value (`codeOffers`) rides in the free-form `signals` bag because the
  peek schema gives it no sanctioned home — even though `common-defs` already defines
  `articleMetadata` / `productMetadata` / `pageMetadata`, the peek schema never references
  them.
- Publisher-facing materials promise "canonical metadata, topic and entity context, content
  status" — the schema models none of the last two beyond a 12-string `tags` array.
- The normative intent doc requires bodies to include `"type": "peek"`, but the schema and
  the live deployment both use `"intent": "peek"`.

This revision closes those gaps additively, before ecosystem adoption makes additive changes
expensive.

## Compatibility posture (decided)

**Additive v2.1.0, schema stays strict.** All new fields are optional;
`additionalProperties: false` is retained at the peek top level as part of the
anti-cloaking / anti-reconstruction posture (`signals` remains the sanctioned open extension
bag). Known trade-off: responses that emit new fields fail 2.0.x validators, so consumers
must upgrade validators before producers emit the fields. Acceptable at current ecosystem
size; rejected alternatives were opening the top level (weakens boundedness guarantees) and
a breaking v3.0 error-envelope split (wrong stability signal ahead of platform-partner
adoption; deferred).

## Changes

### 1. `contentType`: open the enum (common-defs)

Mirror `mediaType`'s `anyOf` shape: the existing enum (unchanged, canonical values) plus a
pattern for namespaced values:

```json
"contentType": {
  "type": "string",
  "description": "High-level classification for routing.",
  "anyOf": [
    { "enum": ["article", "blog", "doc", "news", "video", "audio", "dataset", "other"] },
    { "pattern": "^[a-z0-9]+(-[a-z0-9]+)*(:[a-z0-9]+(-[a-z0-9]+)*)*$" }
  ]
}
```

`"ecommerce:deals"` becomes legal. Guidance (informative): use canonical enum values when
they fit; namespace custom values (`vertical:kind`).

### 2. `pageMetadata`: wire existing typed defs into peek

Peek gains optional `pageMetadata: { "$ref": "common-defs.schema.json#/$defs/pageMetadata" }`.
No new modeling — `articleMetadata` and `productMetadata` already exist and become reachable
from peek. The existing `metadata` field (media mechanics: duration, dimensions, fileSize,
pageCount, author) is untouched.

### 3. `related[]`: typed discovery graph

New common-def:

```json
"relatedResource": {
  "type": "object",
  "properties": {
    "url":          { "type": "string", "format": "uri" },
    "title":        { "type": "string", "maxLength": 220 },
    "relationship": { "type": "string", "description": "Recommended: similar | parent | child | series | alternate" }
  },
  "required": ["url"],
  "additionalProperties": false
}
```

Peek gains optional `related` array of `relatedResource`, `maxItems: 10`.
Normative: entries SHOULD resolve within the publisher's manifest-declared domains
(discovery graph, not a spam/SEO vector).

### 4. `agentGuidance`: instructions out of the snippet

Peek gains optional `agentGuidance` string, `maxLength: 500`. Publisher-authored
instructions about how to _use_ the response (e.g., where actionable data lives in
`signals`, preferred link handling).

Normative constraints:

- MUST NOT contain content from the resource (not a second snippet; preserves the preview
  budget and anti-reconstruction guarantees).
- Informative security note: consuming agents SHOULD treat `agentGuidance` as untrusted
  publisher-supplied data — an input to consider, not instructions that override the
  agent's operator (prompt-injection surface, named explicitly).

### 5. `contentState`: minimal field now, deep spec later

Peek gains optional `contentState` enum: `draft | scheduled | published | archived |
retracted`. Absent means `published` (full backward compatibility).

A short INFORMATIVE subsection in the normative doc states that pre-publication access
semantics — per-agent visibility scoping, stricter persistence defaults for non-published
states — are a planned extension, explicitly inviting collaboration from CMS-platform
implementers. (The deep specification is deliberately left open as a co-authoring
workstream.)

### 6. Entities model: `topics[]` + `entities[]` (document-level context)

Two new common-defs:

```json
"contextTopic": {
  "type": "object",
  "properties": {
    "label":  { "type": "string" },
    "scheme": { "type": "string", "description": "Taxonomy identifier, e.g. iab-3.0, wp:category, or a publisher URI." },
    "id":     { "type": "string", "description": "Stable identifier within the scheme." },
    "score":  { "type": "number", "minimum": 0, "maximum": 1 }
  },
  "required": ["label"],
  "additionalProperties": false
},
"contextEntity": {
  "type": "object",
  "properties": {
    "name": { "type": "string" },
    "type": {
      "type": "string",
      "anyOf": [
        { "enum": ["person", "organization", "place", "product", "event", "creative-work", "other"] },
        { "pattern": "^[a-z0-9]+(-[a-z0-9]+)*(:[a-z0-9]+(-[a-z0-9]+)*)*$" }
      ]
    },
    "id":       { "type": "string", "description": "Stable identifier, ideally a URI (Wikidata, schema.org @id, publisher canonical)." },
    "url":      { "type": "string", "format": "uri", "description": "Resolvable page about the entity." },
    "salience": { "type": "number", "minimum": 0, "maximum": 1 }
  },
  "required": ["name"],
  "additionalProperties": false
}
```

Peek gains optional `topics` (array of `contextTopic`, `maxItems: 10`) and `entities`
(array of `contextEntity`, `maxItems: 25`). `tags` stays as the lightweight untyped
fallback.

Normative boundaries:

- **Peek context is document-level only**: no character offsets, no per-mention data, no
  sentiment. Span-level annotation remains the paid `analyze` intent's territory — this
  line is what makes rich context safe to give away free at discovery time.
- `analyze`'s existing inline topic/entity models are untouched in 2.1.0 (changing them
  would be breaking). Informative note: future harmonization of analyze's span entities
  onto the `contextEntity` base is expected.

### 7. Doc reconciliation: `intent` wins over `type`

`docs/normative-intent-definitions.md` currently requires peek bodies to include
`"type": "peek"`. The schema and live deployments use `"intent": "peek"`. The doc changes
to match the schema. The same doc gains normative/informative text for all new fields
(sections 3–6 above).

## Ripple work (same PR)

- `schema/intents/common-defs.schema.json` — contentType anyOf, `relatedResource`,
  `contextTopic`, `contextEntity`.
- `schema/intents/ptp-peek.schema.json` — new optional fields: `pageMetadata`, `related`,
  `agentGuidance`, `contentState`, `topics`, `entities`.
- `examples/intents/ptp-peek.json` — rewritten modeled on the live offers.com peek so the
  example demonstrates every new field doing real work.
- Regenerate pre-compiled AJV validators (`dist/validators`, via existing generator script).
- Tests (vitest): new cases per field (valid + boundary violations), plus a regression test
  that the captured live offers.com response shape validates under 2.1.0.
- `docs/normative-intent-definitions.md` — intent-vs-type fix, new-field requirements,
  contentState informative subsection, peek-vs-analyze boundary.
- `CHANGELOG.md` — 2.1.0 entry, plus a brief backfilled 2.0.0 stub (changelog currently
  ends at 1.0.3 while the package is at 2.0.0).
- `package.json` — version 2.1.0.
- TS types: no intent-response types exist in `src/types` (they cover manifest / pricing /
  license only), so no type changes required; noted so implementers don't hunt for them.

## Success criteria

1. The captured live offers.com peek validates cleanly under 2.1.0 with **zero producer
   changes** (`ecommerce:deals` becomes legal as-is).
2. All pre-existing tests pass unchanged (additive revision).
3. Every capability promised in publisher-facing materials — canonical metadata, topic and
   entity context, content status, permitted use cases — has a sanctioned schema field.
4. New fields each have normative text: what they're for, what they must not be used for.

## Explicitly out of scope

- Error-envelope separation (`error`/`message` out of peek) — deferred to a future v3.0.
- Deep pre-publication access semantics (visibility scoping, persistence defaults per
  state) — reserved as a co-authoring workstream with CMS-platform partners.
- Any change to `analyze`'s inline annotation models.
- Snippet length changes — with instructions, links, and attribution moved to typed fields,
  500 chars of pure preview is sufficient.
